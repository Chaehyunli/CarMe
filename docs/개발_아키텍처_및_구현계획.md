# CarMe 개발 아키텍처 및 구현 계획

## 1. 결론: 2개 서비스로 시작한다

MVP는 아래처럼 구성한다.

```text
frontend  ──HTTPS──>  backend (FastAPI, RAG 모듈 포함)
                              ├─ PostgreSQL + pgvector
                              ├─ S3-compatible object storage
                              └─ Ollama (로컬 LLM·임베딩)
```

`AI`는 backend 안의 코드 모듈과 문서 적재 명령으로 둔다. 별도 AI 서버는 만들지 않는다.

| 선택지 | 현재 판단 | 이유 |
|---|---|---|
| Frontend + FastAPI backend | 채택 | 여러 매뉴얼을 지원해도 초기 규모에서는 가장 단순하며, 인증·인가와 RAG를 한 서비스에서 관리 가능 |
| Frontend + 일반 backend + AI HTTP service | 보류 | 서비스 간 JWT 전달, 내부 API 보안, 장애 전파, 배포·로그 추적이 늘지만 독립 확장의 이득이 아직 없음 |
| FastAPI 내부 async worker | 조건부 채택 | PDF 적재·임베딩은 웹 요청과 분리해 CLI 또는 worker로 실행. 초기에는 같은 이미지의 별도 명령으로 충분 |

AI 서비스 분리는 아래 중 하나가 실제 문제가 되는 시점에 한다.

- 임베딩/재색인이 API worker를 장시간 점유한다.
- GPU 추론을 독립적으로 늘려야 한다.
- 문서 적재와 상담 API의 배포 주기·권한·스케일 요구가 달라진다.
- 여러 차종과 동시 요청 증가로 retrieval worker pool이 필요해진다.

## 3. Docker Compose 개발 환경

| 컨테이너 | 역할 | 영속 볼륨 |
|---|---|---|
| `db` | PostgreSQL 관계 데이터, pgvector, Alembic migration 대상 | `db_data` |
| `minio` | S3 호환 private object storage | `minio_data` |
| `ollama` | API 전용 로컬 생성·임베딩 모델 서버 | `ollama_data` |

개발에서는 `docker compose up -d`로 `db`, `minio`, `ollama`만 실행한다. FastAPI와 Vue/Vite는 각각 host의 Python/Node 개발 서버로 실행하며, 자세한 절차는 `backend/README.md`, `frontend/README.md`를 따른다. backend Dockerfile은 후속 배포 이미지 용도로만 유지한다.

MVP에서 Redis, Kafka, Elasticsearch, 별도 벡터 DB는 넣지 않는다. Elasticsearch는 [인프라·검색·로컬 AI 선정](./인프라_및_로컬AI_선정.md)의 품질·규모 기준이 발생할 때만 별도 search 서비스로 추가한다. background job이 필요해지는 시점에만 Redis + worker를 추가한다.

필수 환경 변수는 다음처럼 이름만 `.env.example`에 두고 실제 값은 비밀 저장소에 둔다.

## 4. 관리자 카탈로그와 문서 적재 운영 절차

일반 사용자는 차량을 등록하고 상담만 한다. `ADMIN` 역할은 별도 운영 화면에서 차량 카탈로그와 매뉴얼을 관리한다. 역할 부여는 migration/초기 운영 절차로만 수행하며, 일반 API에서 역할을 바꾸는 기능은 만들지 않는다.

- 관리자는 `model_name = 아반떼`, `model_year = 2025`를 하나의 `vehicle_catalog` 행에 입력한다. 서버는 화면용 `display_name = 아반떼 2025`를 생성한다. 내부 코드와 S3 object key는 운영 화면에 표시하지 않는다.
- 차량 카탈로그는 처음 `DRAFT`다. 기본 매뉴얼이 `READY`가 된 뒤에만 `ACTIVE`로 공개한다.
- 관리자는 PDF를 private bucket에 browser direct upload 한다. API는 고유 staging object에 한정한 짧은 만료 PUT presigned URL만 발급하고, 완료 신호 후 worker가 파일 타입·크기·SHA-256·PDF 페이지 수를 재검증한다.
- 초기에는 변경 요청을 actor·대상·request ID·결과와 함께 구조화 로그에 남긴다. `READY` 문서는 덮어쓰지 않고 개정 PDF를 새 매뉴얼 버전으로 적재한다.

`CN7_2025_ko_KR.pdf`는 첫 적재 검증 파일이다. 이후 모든 대상 모델·연식 매뉴얼을 같은 규칙으로 MinIO/S3 private bucket에 업로드한다. 개발용 object key도 운영과 동일하게 유지한다.

```text
manuals/hyundai/{model-code}/{model-year}/{locale}/{manual-type}/{source-filename}.pdf
```

적재 명령은 재실행 가능(idempotent)해야 한다.

1. 파일 크기, MIME type, SHA-256, 페이지 수를 검증한다.
2. `manual` 레코드를 `UPLOADED`로 만든다. 동일 해시가 `READY`면 중단한다.
3. 페이지 텍스트를 추출하고 목차 섹션을 구성한다.
4. 섹션·페이지를 기준으로 한 PDF 페이지 안에서 청킹하고 `manual_chunk.pdf_page_number`에 페이지 번호를 저장한다.
5. 임베딩 생성 후 `manual_chunk.embedding`을 저장한다.
6. 20개 표본을 확인하고 평가 세트를 실행한다.
7. 평가 기준 통과 시에만 `READY`, 실패하면 `FAILED`와 오류 내용을 기록한다.

`READY` 문서만 검색할 수 있다. 적재 중인 문서는 고객 질문에 노출하지 않는다.

## 5. RAG 구현 계약

FastAPI API 요청에서 아래 모듈 순서를 고정한다.

```text
authorize chat session
  → append in-memory user message
  → safety / ambiguity classifier
  → DB로 선택 차량의 applicable manual ID 결정
  → 목차 섹션 1차 검색
  → 해당 섹션의 페이지 청크 2차 pgvector 검색·재정렬
  → evidence threshold check
  → LangChain grounded generation
  → citation/claim validation
  → append in-memory response + structured retrieval log
```

- `ManualResolver`는 검색 전에 선택한 `vehicle.catalog_id`와 `manual.status = READY`를 필터링해 manual ID를 결정한다. 이 결정은 LLM이나 벡터 검색에 맡기지 않는다.
- `SectionRetriever`는 해당 manual ID의 `manual_section`만, `ChunkRetriever`는 선택 section ID와 manual ID의 `manual_chunk`만 검색한다.
- pgvector는 초기에는 cosine distance와 exact search로 시작하고, 데이터·성능 검증 뒤 HNSW 인덱스를 추가한다.
- LangChain은 순서가 고정된 LCEL `Runnable` 체인으로 사용한다. 자율 Agent, 무제한 tool call, 요청 시 PDF 전체 로드는 사용하지 않는다.
- `RunnableWithMessageHistory`와 `InMemoryChatMessageHistory`는 server `SessionStore`에 연결한다. 최근 4개 메시지/2,000 토큰만 보관하고 DB에는 질문·답변·citation을 쓰지 않는다.
- 이 선택은 MVP에서 API process/worker 1개로 운영한다는 제약을 가진다. 재시작·배포·다중 replica에서는 세션이 종료되며, 확장 시 Redis 또는 영속 세션 저장소를 별도 설계한다.
- `top_k`, threshold, prompt, 임베딩 모델은 코드 상수가 아닌 버전이 있는 설정값으로 저장한다.
- citation은 `manual_chunk` 원문 안의 실제 substring만 허용한다.
- LLM 오류·timeout·검증 실패도 `INSUFFICIENT_EVIDENCE`로 안전하게 종료하고 내부 오류 ID만 로그에 남긴다.

## 6. 구현 순서

### Phase 0 — 관리자 데이터 준비

1. 초기 `ADMIN` 계정을 안전하게 부여하고, `model_name = 아반떼`, `model_year = 2025` 차량 카탈로그 행을 `DRAFT`로 만든다.
2. 관리자 화면에서 CN7 PDF를 첫 검증 파일로 private MinIO bucket에 올리고, 이후 대상 매뉴얼을 같은 방식으로 적재한다.
3. 각 PDF에서 텍스트 추출·페이지 수·파일 해시를 검증한다. CN7은 444쪽 전부가 처리되는지 확인한다.
4. 매뉴얼마다 대표 페이지 20개로 PDF 쪽수·본문 쪽수 대응을 확인한다.
5. 매뉴얼마다 60개 평가 질문과 기대 상태·정답 페이지를 만들고, 확인한 뒤 차량 카탈로그를 `ACTIVE`로 공개한다.

### Phase 1 — 최소 수직 흐름

1. PostgreSQL schema/migration, `ADMIN` 인가, MinIO 연결, 관리자 매뉴얼 upload/적재 요청 구현
2. 카카오 OAuth, JWT, vehicle 소유권 검증
3. 적재 완료된 모델·연식 목록 조회, 차량 등록, 메모리 세션 생성, 질문 처리
4. pgvector 검색과 `GROUNDED`/`INSUFFICIENT_EVIDENCE` 상태 반환
5. 근거 카드와 presigned PDF URL

### Phase 2 — 출시 안전성

1. `AMBIGUOUS`, `SAFETY_ESCALATION` 화면과 서버 규칙
2. 세션 만료/종료 UI, 차량 삭제·계정 삭제 정책
3. API 권한 테스트, 원문 인용 검증 테스트, 평가 세트 회귀 테스트
4. 모바일 글자 크기·대비·버튼 영역 점검

### Phase 3 — 확장 전 검토

새 차종·연식을 추가할 때마다 차량 선택값, `manual_applicability`, 적재 idempotency, 평가 게이트를 함께 적용한다. 가격표 수집·옵션 설치 판별·실시간 차량 연동은 별도 제품 단계로 둔다.

## 7. 필수 테스트

| 계층 | 확인 항목 |
|---|---|
| 적재 | 중복 해시 차단, 목차-섹션-페이지 연결, 페이지 수, 빈 페이지 상태, 청크의 단일 페이지 연결 |
| RAG | 선택 차량 매뉴얼 결정, 목차 섹션 1차 검색, 페이지 청크 2차 검색, 미근거 질문 폴백, 옵션 장착 여부 미판정 고지 |
| 인용 | 스니펫이 원문 substring인지, PDF 페이지가 실제 페이지인지 |
| API | 401/403, 타 사용자 IDOR 차단, 상태별 응답 schema |
| 스토리지 | bucket public read 차단, 사용자 download·관리자 upload presigned URL 만료, object key 비노출 |
| 관리자 | 일반 사용자 admin API 차단, 기본 `READY` 매뉴얼 전 공개 차단, 상태 전이·구조화 로그·개정본 새 버전 확인 |
| 회귀 | 60개 평가 세트의 정답성·안전성·인용성 기준 |
